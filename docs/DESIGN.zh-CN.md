# Python Gitlet 设计说明

## 模块与职责

`gitlet/cli.py` 检查命令名、参数和初始化状态，然后调用仓库方法。
`GitletError` 表示课程定义的预期失败，由入口统一打印。
`gitlet/__main__.py` 提供模块入口，根目录 `gitlet_cli.py` 提供无需安装的绝对路径入口。

`gitlet/models.py` 提供 `Commit`，包含 `message`、`timestamp`、`parents` 和 `files`。
普通提交有一个父 ID，初始提交没有父 ID，合并提交有两个。
提交采用 `dataclass(frozen=True)`；文件映射在创建新提交时复制，已有提交文件不覆写。
这里的 `frozen` 禁止字段重新赋值，但不会自动冻结内部字典；保持不可变快照是仓库代码的约定。

`gitlet/repository.py` 提供 `Repository`，负责对象落盘、分支指针、暂存区和工作文件。
不为 blob、分支和暂存区额外设计类：blob 是字节串，分支是单个引用文件，
暂存区在内存中是 `dict` 和 `set`。这保留了教学需要的概念，减少样板代码。

## 磁盘布局

```text
工作目录/
├── 用户文件...
└── .gitlet/
    ├── HEAD                 当前分支名，UTF-8 文本
    ├── index.json           暂存新增映射与暂存删除数组
    ├── branches/
    │   ├── ref-master       master 指向的完整提交 ID
    │   └── ref-feature%2Fa  feature/a 指向的完整提交 ID
    ├── commits/
    │   └── <提交 SHA-1>      稳定 JSON 编码的提交元数据
    └── blobs/
        └── <内容 SHA-1>      原始文件字节
```

分支名使用百分号编码并加上 `ref-` 前缀，避免名称变成磁盘上的目录或父目录路径。
HEAD 只保存当前分支名，当前提交通过该分支引用读取，避免保存两个可能不一致的头指针。

暂存区的逻辑格式：

```json
{"add": {"note.txt": "<blob ID>"}, "remove": ["old.txt"]}
```

提交的逻辑格式：

```json
{
  "message": "完成解析器",
  "timestamp": 1790936130000000000,
  "parents": ["<第一父 ID>", "<第二父 ID>"],
  "files": {"note.txt": "<blob ID>"}
}
```

实际 JSON 使用排序的键和紧凑分隔符；非 ASCII 字符转义，从而得到确定的 UTF-8 字节。
父提交和 blob 只以 ID 字符串引用，不嵌入对象，也不重复保存祖先历史。
时间以 Unix epoch 后的纳秒整数保存；初始提交固定为 0。

## 内容寻址与快照

blob ID 为 `sha1(原始文件字节)`，不包含文件名；不同文件名可以共享同一个 blob。
commit ID 为 `sha1(完整稳定 JSON 字节)`，包含全部元数据、父 ID 顺序及文件映射。
字典的插入顺序不影响 JSON 或 ID，时区只影响显示，不影响已保存的时间值。

`add` 时就保存 blob，并在暂存区记录 ID。`commit` 无需读取工作文件，只复制父快照映射并应用暂存区。
对象文件已存在时跳过写入。这样新提交仅增加元数据，文件内容不会因为继承被重复存储。
未被最终提交采用的暂存 blob 会保留；本项目没有垃圾回收。

完整 ID 直接通过文件路径读取。缩写 ID 扫描提交目录，只有唯一匹配才接受。
不接受空 ID、超过 40 位或非小写十六进制字符。

## 工作目录修改

分支切换与重置共享 `restore_tree`：先取得当前和目标映射，检查目标文件是否会覆盖未跟踪文件，
检查通过后删除当前独有的已跟踪文件，再写入目标文件，并清空暂存区。
分支切换改变 HEAD 的分支名；重置更新当前分支指向的提交。

单文件恢复不修改暂存区或指针。`rm` 只删除当前提交跟踪的工作文件。
工作文件参数经过平面文件名检查，不能访问父目录或 `.gitlet` 元数据。
符号链接不参与跟踪；恢复遇到符号链接或同名目录时拒绝覆盖。

课程定义的参数和状态错误在变更之前检查。合并也先生成全部计划并做覆盖检查。
实现不包含文件锁、写入中断恢复或跨文件事务，因此以单进程、正常磁盘读写为使用前提。

## 合并算法

使用队列沿两个父节点广度优先遍历，计算两边的祖先集合与最短距离。
两集合交集得到共同祖先。再从所有共同祖先的父节点出发遍历，标记“更旧的祖先”，
把这些节点从候选中排除。剩余节点正是最近共同祖先。
多个候选按当前侧距离、目标侧距离、ID 排序选择，结果确定。

不能简单选择距当前头最近的共同祖先：合并的第二父链可能跳过很多提交，
使较旧的祖先反而更近。测试中特意构造了这种图。
全部遍历采用循环并记录已访问节点，避免长历史的递归溢出或重复遍历。

对每个文件，用共同祖先 B、当前 C、目标 G 的 blob ID 比较；不存在用 `None` 表示，
因此空文件与缺失文件能被区分。

1. `C == G` 或 `G == B`：保持当前状态。
2. `C == B`：应用目标状态；目标缺失则删除。
3. 其他情况：冲突，拼接标记和两侧提交内容。

这三步覆盖独立新增、同样修改、删除、修改/删除冲突等情况。
先收集改写和删除计划，然后检查所有受影响文件，最后一次写入暂存区并调用提交逻辑。
合并提交的父 ID 顺序固定为当前头、目标头。冲突标志在任意文件冲突后保持为真。

如果没有计划中的改写或删除，按课程规则报告没有暂存变化。
如果当前头是目标头的祖先，则采用 SP21 说明中的 `checkout` 快进约定，切换当前分支名。

## 成本与简化边界

令 F 为快照中的文件条目数量，S 为暂存条目数量，N 为相关历史提交数量，
W 为读取或写入的文件总字节数。下表计入 Python 实际 JSON 处理成本；
课程分析允许忽略元数据序列化/反序列化成本。

| 操作 | 主要成本 |
| --- | --- |
| `init` | 固定数量的目录、对象和引用写入 |
| `add` | 读取和哈希单文件；另有当前映射与暂存 JSON 的处理 |
| `commit` | `O(F + S)` 的映射更新，再进行 JSON 键排序；不扫描历史或读取全部 blob |
| `rm` | 映射查找与单文件删除；另有元数据处理 |
| `branch` / `rm-branch` | 单个引用文件操作，不遍历历史或全部分支 |
| `log` | 沿第一父链逐个读取元数据，不读取 blob |
| `global-log` / `find` | 线性遍历所有提交元数据，不额外排序 |
| `status` | 快照与暂存状态、工作文件内容、分支列表及输出排序 |
| 分支 `checkout` / `reset` | 当前和目标快照元数据与目标文件字节量；完整 ID 不扫描历史 |
| 单文件 `checkout` | 目标元数据与一个文件内容；缩写 ID 额外扫描提交目录 |
| `merge` | 祖先图线性遍历、文件名排序、需要应用或冲突的文件内容 |

为了稳定哈希与规定的状态输出，JSON 键排序和状态条目排序各自引入排序成本。
历史遍历只读取 commit 元数据，不加载整棵提交图的所有 blob；文件处理才读取所需 blob。
内容去重是主要空间约束，所有提交的祖先对象始终保留。

本实现面向学习：不递归跟踪目录、不保存文件权限、没有索引锁、没有差异压缩和远程协议。
这些边界不妨碍本地命令和课程快照/分支/合并模型。
